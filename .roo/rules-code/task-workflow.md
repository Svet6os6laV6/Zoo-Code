# Task Implementation Workflow

Code реализует ровно одну единицу реализации, назначенную программным harness.

Идентичность задачи, выбор task root, вычисление dependency readiness,
назначение implementation unit, маршрутизация этапов и lifecycle-переходы
выполняются harness.

## Контекст задачи

Используй runtime-поля `Current task` и `Task artifacts` без изменений и в
соответствии с `.roo/rules/task-artifacts.md`.

Запрещено:

- определять `Task` по Git или имени ветки;
- строить task path из `TASK_STATE_V2`;
- искать другую папку задачи;
- выбирать `Txx` самостоятельно;
- вычислять readiness;
- изменять `Current Task` ради scheduling.

Сначала открой канонический `README.md` в переданном task root.

Поле `Task` должно точно совпадать с runtime-полем `Current task`. При
несовпадении сообщи об identity error и не пытайся исправить или угадать
идентичность задачи.

## Вход в Code

Обычный вход в implementation unit:

```text
Status: IMPLEMENTATION
Current Task: implementation/Txx-*.md
```

Реализуй только `Txx`, назначенный через `Current Task`.

Code также может быть запущен harness для fix pass в одном из marker-статусов:

- `REFACTOR`;
- `REVIEW`;
- `QA_READY`.

Правила fix pass описаны ниже.

Если Code запущен при несовместимом lifecycle-статусе и это не fix pass:

- не изменяй production-код;
- не изменяй артефакты;
- перечитай фактическое устойчивое состояние;
- верни его через `TASK_STATE_V2` с:

```text
Stage Result: NOT_APPLICABLE
```

Не записывай `Status` и `Current Task`: маршрут принадлежит harness.

Если обязательные артефакты отсутствуют, не реконструируй план и не выбирай
работу самостоятельно. Зафиксируй blocker metadata и верни:

```text
Stage Result: BLOCKED
Failure Key: missing-required-artifacts
```

Отсутствие обязательного артефакта — реальное препятствие, а не причина
переписывать lifecycle state.

## Начало Code-сессии

Перед изменением production-кода:

1. прочитай `README.md`;
2. прочитай назначенный `implementation/Txx-*.md`;
3. прочитай только дополнительные артефакты, необходимые этому `Txx`;
4. проверь указанные файлы, символы, контракты и допущения в актуальном коде;
5. проверь состояние рабочего дерева через `git status`.

Не загружай автоматически:

- все `Txx`;
- весь `implementation-plan.md`;
- все research-артефакты;
- нерелевантную историю `handoff.md`.

Назначенный `Txx` — основной task-specific контекст. Исходный код остаётся
источником истины.

## Статус текущего `Txx`

Перед изменением production-кода переведи назначенный `Txx` в:

```text
## Status
Status: IN_PROGRESS
```

если он ещё не находится в этом состоянии.

Не изменяй статусы других `Txx` ради координации. Readiness и назначение
следующих единиц выполняет harness.

## Проверка зависимостей

Не пересчитывай dependency DAG и не определяй, какой другой `Txx` готов к
выполнению.

Если текущий `Txx` использует результаты предыдущих единиц, выполни только
необходимую семантическую проверку:

- существует ли требуемый результат или контракт;
- соответствует ли текущий код ожидаемому контракту;
- соответствует ли `Consumes` фактическому `Produces`.

Если расхождение локально и не меняет декомпозицию, обнови только затронутые
семантические поля и продолжай.

Если назначенная единица не может быть реализована, пока не завершена другая
единица `implementation/` (обнаружена внутренняя зависимость), не возвращай
`BLOCKED`. Зафиксируй зависимость и прогресс в текущем `Txx` и верни:

```text
Stage Result: RESCHEDULE_REQUIRED
```

Harness сам запаркует единицу (`IN_PROGRESS` → `TODO`), сбросит назначение и
пересчитает DAG; единица снова станет готовой после завершения зависимости.

Если contract drift ломает декомпозицию, порядок выполнения или integration
boundaries, следуй разделу «Повторный анализ».

## Fix pass

Harness запускает Code в marker-статусе этапа, который запросил исправление:

| Запросивший этап | Результат этапа           | Marker-статус для Code |
| ---------------- | ------------------------- | ---------------------- |
| Refactor         | `FUNCTIONAL_DEFECT`       | `REFACTOR`             |
| Reviewer         | `REQUIRED`                | `REVIEW`               |
| Reviewer         | `PRODUCTION_FIX_REQUIRED` | `REVIEW`               |
| QA               | `FAILED`                  | `QA_READY`             |

Fix pass не входит в implementation DAG и не требует создания отдельного
`Txx`.

При fix pass:

1. прочитай durable finding из артефакта запросившего этапа и `handoff.md`;
2. проверь, что дефект и ожидаемый результат описаны однозначно;
3. исправь только зафиксированный дефект;
4. запусти релевантные проверки;
5. обнови `handoff.md` фактическим результатом;
6. верни `Stage Result: COMPLETED`.

Не создавай fix-`Txx`, не изменяй `Status` и `Current Task` и не назначай
дальнейшую работу. Harness вернёт задачу на запросивший этап для повторной
проверки.

Если finding недостаточно конкретен для безопасного исправления, зафиксируй
blocker metadata и верни `Stage Result: BLOCKED` со стабильным `Failure Key`.

## Scope

Реализуй только текущий `Txx` или конкретный finding текущего fix pass.

Запрещено без необходимости:

- расширять scope;
- рефакторить нерелевантный код;
- исправлять посторонние дефекты;
- выполнять задачи из других `Txx`.

Если артефакт конфликтует с кодовой базой:

1. проверь фактическую реализацию;
2. считай актуальный код источником истины;
3. определи, является ли расхождение локальным или архитектурным;
4. обнови только затронутые артефакты;
5. при архитектурном расхождении следуй разделу «Повторный анализ».

## Состояние рабочего дерева

Перед изменениями выполни:

```sh
git status
```

Существующие изменения могут принадлежать пользователю. Не изменяй, не удаляй
и не перезаписывай нерелевантные правки.

Если пользовательские изменения пересекаются с текущим scope и безопасно
продолжить нельзя, зафиксируй точный конфликт и верни `Stage Result: BLOCKED`.

Перед созданием нового service, interface, DTO, repository или abstraction
проверь, нет ли в проекте подходящего существующего механизма.

## Точечная проверка перед реализацией

Перед внесением изменений:

1. прочитай назначенный `Txx`;
2. открой указанные файлы и символы;
3. проверь текущее поведение и требуемые контракты;
4. выборочно изучи nearby tests;
5. проверь dependency outputs, если `Txx` их потребляет;
6. только после этого изменяй код.

Предпочитай targeted inspection широкому исследованию репозитория.

Широкое исследование допустимо только при конкретной причине:

- в `Txx` недостаточно информации;
- код противоречит артефакту;
- допущение нельзя проверить локально;
- tests или build выявили неожиданную зависимость;
- обнаружен архитектурный конфликт.

Не повторяй Sublimation discovery без необходимости.

## Реализация

Учитывай, когда это относится к текущему scope:

- error handling;
- transactions;
- concurrency;
- idempotency;
- retries;
- backward compatibility;
- external side effects;
- observability;
- миграции и rollback-поведение.

Артефакты описывают intent и контракты. Конкретное решение должно учитывать
фактическую архитектуру и текущий код проекта.

## Проверка результата

После реализации запусти релевантные project checks.

Минимально проверь:

- изменённое поведение;
- затронутые существующие тесты;
- новые regression-сценарии;
- совместимость с контрактами, которые потребляют другие единицы.

Не устанавливай `Status: DONE` для `Txx`, если обязательные проверки падают.

Если проверку невозможно запустить, явно зафиксируй:

- какую проверку не удалось выполнить;
- конкретную причину;
- что было проверено вместо неё;
- остающийся риск.

Если без этой проверки нельзя достоверно подтвердить требуемое поведение,
оставь `Txx` незавершённым и верни `Stage Result: BLOCKED`.

## Завершение текущего `Txx`

После успешной реализации и достаточной проверки:

1. зафиксируй фактический результат в текущем `Txx`;
2. обнови `Produces`, если результат используют downstream-единицы;
3. зафиксируй значимый contract drift;
4. обнови `handoff.md`;
5. установи текущему `Txx`:

```text
## Status
Status: DONE
```

После этого верни `Stage Result: COMPLETED`.

Не:

- выбирай следующий `Txx`;
- рассчитывай readiness других `TODO`;
- записывай другую единицу в `Current Task`;
- запускай следующую implementation unit самостоятельно.

После результата `COMPLETED` harness перечитает snapshot, вычислит readiness и
назначит следующую готовую единицу. Если все обязательные единицы завершены,
harness переведёт задачу в `READY_FOR_REFACTOR` и запустит Refactor.

## Распространение изменений контрактов

Обновляй только знания, реально влияющие на будущие `Txx`:

- фактический `Produces`;
- затронутые `Consumes`;
- `Constraints`;
- `Context notes`;
- межзадачные отклонения в `handoff.md`.

Не копируй историю реализации или production-код в артефакты.

Не изменяй статусы будущих `Txx` ради координации.

### Повторный анализ

Повторный архитектурный анализ требуется, если contract drift:

- ломает текущую декомпозицию;
- меняет границы нескольких единиц;
- создаёт или обнаруживает некорректный dependency graph;
- существенно меняет integration contracts;
- делает будущие `Txx` небезопасными в текущем виде.

Code не выполняет ручной переход `IMPLEMENTATION -> ANALYSIS`, не изменяет
`Current Task` и не перепроектирует будущие единицы молча.

Вместо этого:

1. зафиксируй обнаруженный drift и его влияние в `handoff.md`;
2. укажи, какие части плана требуют пересмотра;
3. не изменяй будущие `Txx`, если их корректный контракт больше нельзя
   определить локально;
4. верни:

```text
Stage Result: BLOCKED
Failure Key: implementation-plan-invalidated
```

Harness записывает `Status: BLOCKED`. Возврат задачи в Sublimation должен быть
выполнен отдельным поддерживаемым lifecycle-действием после подтверждения
повторного анализа. До появления такого программного перехода модель не должна
имитировать его изменением `README.md`.

## Завершение implementation-этапа

Code не определяет самостоятельно, является ли текущий `Txx` последним готовым
элементом DAG. Это проверяет scheduler после `Stage Result: COMPLETED`.

Если для всей задачи нужны финальные implementation-checks, они должны быть:

- частью `Verification` последнего зависимого `Txx`; или
- отдельным осмысленным integration-`Txx`, созданным Sublimation.

Code не запускает Refactor или Reviewer самостоятельно и не записывает переход
в `READY_FOR_REFACTOR`.

## BLOCKED

Используй `BLOCKED` только при реальном проверяемом препятствии, которое harness
не может устранить самостоятельно: нужно решение пользователя, отсутствует
credential, недоступен внешний сервис или требование неоднозначно.

Внутренняя, устранимая причина — назначенная единица зависит от другой единицы
`implementation/` — оформляется как `RESCHEDULE_REQUIRED`, а не `BLOCKED`.
`BLOCKED` для такой причины останавливает lifecycle и создаёт deadlock, потому
что зависимость, которая сама является `TODO`-единицей, не сможет завершиться,
пока задача заблокирована.

Не выдавай частично реализованный `Txx` за `DONE`.

Заполни blocker metadata согласно `.roo/rules/task-artifacts.md` и сохрани
полезный контекст в текущем `Txx` и `handoff.md`:

```text
Blocked From: <observed TASK_STATUS>
Blocker: <verifiable reason>
Unblock Condition: <what must become true>
```

Перед завершением верни в составе `TASK_STATE_V2`:

```text
Stage Result: BLOCKED
Failure Key: <stable finding id>
```

Не записывай `Status: BLOCKED` самостоятельно. Это делает harness.

## Handoff

В `<Task artifacts>/handoff.md` сохраняй только информацию, необходимую
следующим сессиям:

- что реализовано;
- что проверено;
- фактические контракты;
- значимые отклонения от плана;
- известные ограничения;
- blockers и follow-up.

Не сохраняй chain-of-thought, историю чата и рутинный журнал действий.

## Завершение сессии

Перед завершением:

1. убедись, что текущий `Txx` или finding отражает фактический результат;
2. зафиксируй verification;
3. распространи только значимый contract drift;
4. обнови `handoff.md`, если информация нужна следующим этапам;
5. перечитай каноническое состояние задачи;
6. верни `TASK_STATE_V2` согласно `.roo/rules/task-artifacts.md`.

`TASK_STATE_V2` сообщает semantic result и наблюдаемое durable lifecycle state.
Он не используется моделью для scheduling `Txx`, выбора следующего mode или
записи lifecycle-перехода. Эти решения принимает программный lifecycle
controller.
