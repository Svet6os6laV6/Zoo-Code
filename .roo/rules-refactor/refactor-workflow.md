# refactor-workflow

Refactor mode используется только после завершения основной реализации задачи.

Цель — улучшить качество фактических изменений без изменения наблюдаемого
поведения системы.

## Task Context

Использовать runtime `Current task` и `Task artifacts` согласно
`.roo/rules/task-artifacts.md`.

Сначала прочитать `README.md` из переданного `Task artifacts` и убедиться, что
его `Task` совпадает с runtime `Current task`.

Допустимые входные статусы:

- `READY_FOR_REFACTOR` — проверить завершённость реализации и выполнить Refactor;
- `REFACTOR` — продолжить прерванную Refactor-сессию.

`Status`, `Current Task` и `Failure Attempts` не изменять: ими владеет harness.

При любом другом статусе ничего не менять и вернуть `TASK_STATE_V2` с
`Stage Result: NOT_APPLICABLE`. Это не `BLOCKED`.

## Before Refactoring

Перед изменениями:

1. проверить `git status` и не затрагивать нерелевантные пользовательские правки;
2. изучить финальный diff задачи;
3. изучить связанные тесты;
4. убедиться, что основная реализация завершена;
5. убедиться, что релевантные тесты проходят.

Основной scope рефакторинга — изменения текущей задачи.

Не выполнять общий cleanup кодовой базы.

## Refactoring Goals

Проверить изменения на:

- дублирование логики;
- избыточную вложенность и сложные условия;
- неясные имена;
- слишком большие функции или методы;
- смешение ответственностей;
- ненужные абстракции и неверные границы;
- повторяющиеся константы и magic values;
- неудобную обработку ошибок;
- лишние преобразования;
- код, который можно упростить без потери ясности;
- несоответствие существующим паттернам проекта.

Предпочитать простые решения и существующие проектные абстракции.

Не создавать новые уровни абстракций без реальной необходимости.

## Behavior Preservation

Рефакторинг не должен менять:

- business behavior;
- API contracts;
- database semantics;
- event semantics;
- retry behavior;
- transaction boundaries;
- concurrency guarantees;
- idempotency guarantees.

Если для корректности требуется изменить поведение, это функциональный дефект,
а не refactoring.

В таком случае:

1. остановить рефакторинг и не исправлять дефект в Refactor mode;
2. записать finding в `handoff.md`;
3. вернуть:

```text
Stage Result: FUNCTIONAL_DEFECT
Failure Key: <stable finding id>
```

Harness запустит Code в marker-статусе `REFACTOR`, а после
`Stage Result: COMPLETED` вернёт задачу в Refactor для повторной проверки.
Fix-`Txx` не создаётся.

## Scope

Разрешены изменения:

- файлов, напрямую затронутых текущей задачей;
- небольшого числа прямых зависимостей, если это необходимо для чистого решения.

Не выполнять:

- нерелевантный cleanup;
- массовые rename;
- форматирование всего проекта;
- архитектурную перестройку вне scope задачи;
- обновление зависимостей без необходимости.

## Verification

После рефакторинга:

1. проверить финальный `git diff`;
2. убедиться, что случайные behavioral changes не появились;
3. запустить релевантные тесты;
4. запустить static analysis и lint, если они настроены в проекте.

Если тесты падают из-за refactoring:

- не считать этап завершённым;
- исправить regression или удалить только проблемную часть своих изменений;
- повторно запустить проверки.

Если тесты выявили существующий функциональный дефект, использовать
`Stage Result: FUNCTIONAL_DEFECT`, а не исправлять его в Refactor mode.

## Completion

После успешного refactoring:

1. обновить `handoff.md`;
2. кратко зафиксировать выполненные улучшения и проверки;
3. перечитать `README.md`;
4. вернуть `TASK_STATE_V2` с `Stage Result: COMPLETED`;
5. не запускать Reviewer самостоятельно.

Переход в `READY_FOR_REVIEW` и запуск Reviewer выполняет harness.

Если Refactor не может завершиться из-за внешнего blocker, отсутствующего
решения или конфликтующих требований:

1. записать blocker metadata по `.roo/rules/task-artifacts.md` в `handoff.md`;
2. вернуть:

```text
Stage Result: BLOCKED
Failure Key: <stable blocker id>
```

`Status: BLOCKED` запишет harness.
