# Sublimation Task Analysis

## Goal

Исследовать backend-задачу до реализации и подготовить артефакты, достаточные\
для независимых Code-сессий.

Не изменять production-код.

## Task input sources

Использовать источники в таком порядке:

1. исходную цель пользователя, приложенные материалы и явно указанные ссылки;
2. фактическое состояние текущей ветки, commits, diff относительно base branch\
   и доступные issue/MR metadata;
3. документацию проекта, production-код, конфигурацию и тесты;
4. дополнительные артефакты, явно указанные пользователем.

Не подменять запрос случайным файлом из `plans/` или другой папки.

Если данных недостаточно для определения scope или `Expected behavior`, не\
угадывать. Зафиксировать blocker по `.roo/rules/task-artifacts.md` и запросить\
конкретную недостающую информацию.

## Analysis

Перед проектированием решения:

1. изучить постановку задачи;
2. найти релевантную область кодовой базы;
3. определить `Current behavior`;
4. определить `Expected behavior`;
5. зафиксировать расхождение между ними;
6. проследить основной data/control flow;
7. определить затронутые компоненты и зависимости;
8. изучить существующие тесты.

Sublimation выполняет broad discovery один раз для всей затронутой области, не\
исследуя нерелевантные части репозитория.

Когда это применимо, проверить:

- entry points и execution flow;
- module boundaries и направление зависимостей;
- interfaces, repositories и внешние integrations;
- state transitions и error handling;
- configuration и существующие patterns;
- concurrency, lifecycle и shutdown behavior.

После discovery применять semantic compression: сохранять только необходимую\
семантику, contracts, constraints и точные ссылки на файлы и символы.

Для HTTP API проверить Swagger/OpenAPI, endpoints и request/response DTO.

Для stateful-логики проверить transactions, concurrency, idempotency, retries,\
locks, partial failures и state transitions.

## Artifacts

Использовать runtime `Task artifacts` согласно `.roo/rules/task-artifacts.md`.

Минимальный набор:

- `README.md`;
- `implementation-plan.md`;
- `handoff.md`;
- минимум один `implementation/Txx-*.md`.

Новые артефакты используют `Protocol Version: 2`.

Дополнительные `context.md`, `sublimationure.md`, `api.md`,\
`data-and-state.md` и `tests.md` создавать только при реальной необходимости.

`implementation-plan.md` — orchestration map, а не research dump. Для\
нескольких `Txx` он отражает:

- декомпозицию;
- зависимости и integration relationships;
- порядок или waves;
- fork/join и integration points;
- независимые части;
- contracts/results между `Txx`.

Выводы, необходимые конкретному `Txx`, должны находиться внутри этого `Txx`.

## Decomposition

Создать минимум одну implementation task: `T01-*.md`.

Декомпозировать задачу рекурсивно до минимальных законченных и отдельно
проверяемых единиц реализации.

Цель декомпозиции — уменьшить объём работы и контекста одной Code-сессии, а не
минимизировать количество `Txx`.

`Txx` не обязана:

- иметь самостоятельную бизнес-ценность;
- быть независимой от других `Txx`;
- выполняться параллельно;
- представлять целую capability.

Последовательная цепочка небольших задач является нормальной:

`T01 → T02 → T03 → T04`.

Каждый `Txx` должен иметь:

- одну основную ответственность;
- один конкретный технический результат;
- ограниченную область изменений;
- собственный проверяемый `Verification`;
- ясные `Consumes` и `Produces`, если результат используется другими единицами.

Продолжай разделение, если внутри одной `Txx` присутствуют несколько
самостоятельно реализуемых или проверяемых частей, например:

- domain/model и storage;
- storage и service behavior;
- service behavior и runtime wiring;
- configuration и использование конфигурации;
- transport/API и application logic;
- несколько независимых integration points;
- основной happy path и значимая отдельная error/retry/concurrency логика;
- реализация механизма и отдельная integration verification;
- несколько изменений, каждое из которых создаёт результат, используемый
  следующим шагом.

Если реализацию можно естественно выполнить как:

1. создать контракт;
2. реализовать механизм;
3. подключить механизм;
4. интегрировать его;
5. проверить интеграцию;

предпочитай отдельные `Txx`, а не одну большую задачу.

Не объединяй несколько шагов только потому, что они относятся к одной feature.

### Stop condition

Прекратить декомпозицию, когда дальнейшее разделение привело бы к задачам,
которые:

- не имеют собственного проверяемого результата;
- состоят только из механических действий вроде добавления одного import,
  переименования символа или одной строки;
- невозможно осмысленно завершить и проверить отдельно;
- требуют постоянно изменять один и тот же неделимый contract как единое целое.

Не использовать количество файлов, строк кода или функций как самостоятельный
критерий размера `Txx`.

При сомнении предпочитать меньшую `Txx`.

## Finish

Перед завершением:

- зафиксировать архитектурные решения, риски и проверенные ограничения;
- создать или обновить `implementation-plan.md` и `handoff.md`;
- создать implementation tasks;
- убедиться, что каждой Code-сессии достаточно переданного контекста;
- перечитать канонический `README.md`.

Когда реализация может начинаться, вернуть `TASK_STATE_V2` с\
`Stage Result: COMPLETED`. Lifecycle-переход и назначение первого `Txx`\
выполняет harness.

При отсутствии критической информации записать blocker metadata и вернуть\
`Stage Result: BLOCKED`; `Status: BLOCKED` запишет harness.

Sublimation не запускает следующий mode и не изменяет `Status` или `Current Task`.
