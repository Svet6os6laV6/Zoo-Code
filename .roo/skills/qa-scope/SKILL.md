# QA Scope

## Purpose

Создать финальный QA-документ после завершения реализации.

QA scope описывает изменившееся поведение системы и сценарии проверки, а не
внутреннюю структуру кода.

Сохранить результат в `<Task artifacts>/qa.md`.

## Preconditions

Входной статус должен быть `REVIEW_PASSED`.

При другом статусе:

- не создавать и не обновлять `qa.md`;
- не изменять `README.md` и `handoff.md`;
- не использовать `BLOCKED`;
- не записывать `Status`;
- вернуть `Stage Result: NOT_APPLICABLE` с ожидаемым и фактическим статусом.

Использовать runtime `Current task` и `Task artifacts` согласно
`.roo/rules/task-artifacts.md`.

Перед созданием scope прочитать:

1. `README.md`;
2. `handoff.md`;
3. `tests.md`, если он существует и релевантен.

`Txx` читать только при необходимости понять фактическое изменение или
проверить конфликт с кодом.

Источники истины:

1. фактический `git diff`;
2. текущий production-код;
3. существующие и новые тесты;
4. migrations;
5. Swagger/OpenAPI, если менялся API.

QA scope должен отражать фактическую реализацию, а не только исходный план.

## Analyze Actual Changes

Проверить `git status` и `git diff`.

При необходимости использовать diff относительно фактической base branch, не
предполагая автоматически `master`.

Определить:

- изменённое поведение;
- затронутые business flows;
- изменённые API;
- migrations;
- добавленные или изменённые тесты;
- возможный регресс.

Не перечислять все изменённые файлы без пользы для QA.

## Behavior First

Описывать изменения с точки зрения поведения системы.

Плохо:

`В CardCallbackHandler добавлен вызов DuplicateDepositGuard.`

Хорошо:

`Если заказ уже успешно оплачен через другую платёжную систему, повторная
оплата не должна подтверждаться и должна обрабатываться как дубль.`

Implementation details добавлять только тогда, когда они нужны для проверки.

## Create QA Artifact

Создать или полностью обновить `<Task artifacts>/qa.md`.

Документ должен отражать текущее состояние реализации без истории старых QA
scope.

## QA Document Format

### Что изменилось

Кратко описать изменение поведения системы понятным для QA и менеджера языком.

### Основные сценарии проверки

Для каждого важного сценария указать:

- **Сценарий** — что проверяется;
- **Предусловия** — требуемое состояние;
- **Действие** — что сделать;
- **Ожидаемый результат** — как должна повести себя система.

Не раздувать список. Объединять проверки одного логического поведения.

### Регресс

Перечислить только существующие сценарии, напрямую затронутые изменением.

### Edge Cases

Добавлять только релевантные задаче случаи, например:

- повторный запрос;
- timeout;
- duplicate event;
- пустые данные;
- boundary value;
- уже обработанное состояние;
- concurrent requests.

### API

Создавать раздел только если задача затрагивает HTTP API.

Указать:

- endpoint и method;
- изменённые request/response fields;
- validation;
- status codes;
- authentication/headers, если изменились;
- backward compatibility.

Если задача затрагивает API, но публичный contract не изменился, указать:
`Публичный API contract не изменился.`

### Data / Migration

Создавать раздел только при изменении БД или migrations.

Указать:

- какие данные меняются;
- обработку существующих данных;
- post-migration checks;
- constraints;
- важные значения;
- повторное применение, если релевантно.

Не превращать QA scope в SQL implementation guide.

### Async / Integrations

Создавать раздел при изменении Kafka, queues, cron, external services, payment
systems, OMS или callbacks.

Указать:

- trigger;
- ожидаемый side effect;
- retry behavior;
- duplicate behavior;
- failure behavior, если он изменился.

### Что не требует проверки

Добавлять только если это помогает ограничить scope, например:

- Swagger contract не изменился;
- UI не затронут;
- расчёт цены не изменился.

### Риски / Особое внимание

Указывать только реальные риски, которые QA может проверить функционально.

## QA Scope Quality Rules

QA scope должен быть кратким, конкретным, основанным на фактической реализации,
ориентированным на поведение и полезным QA и менеджеру.

Не включать:

- длинные архитектурные описания;
- каждый изменённый метод;
- внутренние class names без необходимости;
- историю реализации;
- reasoning;
- нерелевантные сценарии.

Предпочитать несколько качественных проверок большому формальному списку.

## Completion

После создания `qa.md`:

1. сверить документ с фактическим `git diff`;
2. убедиться, что покрыты существенные изменения;
3. убрать дублирование;
4. записать `QA Result: PENDING`;
5. обновить `handoff.md` краткой ссылкой: `qa.md — final verification scope`.

`Status`, `Current Task`, `Next Step` и `Failure Attempts` не изменять: ими
владеет harness.

Вернуть `TASK_STATE_V2` с `Stage Result: PENDING`. Harness запишет
`Status: QA_READY` и остановит задачу до решения пользователя.

Не изменять production-код.

Если при подготовке scope подтверждён production defect:

1. не исправлять его в QA mode;
2. записать finding в `qa.md` и `handoff.md`;
3. вернуть:

```text
Stage Result: FAILED
Failure Key: <stable finding id>
```

Harness запустит Code в marker-статусе `QA_READY`, а после
`Stage Result: COMPLETED` вернёт задачу в QA через `REVIEW_PASSED`.
Fix-`Txx` не создаётся.

`PRODUCTION_FIX_REQUIRED` относится к Reviewer и не используется в QA.
