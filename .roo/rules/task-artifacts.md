# Артефакты задачи

Этот файл определяет устойчивую схему артефактов задачи, смысл каждого
артефакта и контракт передачи знаний между режимами.

Определение текущей задачи, выбор корня артефактов, анализ Git-ветки,
вычисление готовности `Txx`, назначение следующего `Txx`, маршрутизация этапов,
канонические переходы `Status`, возврат после исправлений и ограничение числа
повторных попыток являются ответственностью программного harness.

Модель не должна повторно реализовывать эти механизмы в rules, skills или
тексте артефактов.

## Runtime-контекст задачи

Harness передаёт доверенные runtime-метаданные:

```text
Current task: <TASK>
Task artifacts: .roo/tasks/<TASK>/
```

`Current task` — единственный источник идентичности текущей задачи для rules и
skills. Значения `Current task` и `Task artifacts` считаются авторитетными и
неизменяемыми в рамках текущего запуска.

Запрещено:

- определять задачу по Git-ветке;
- искать другой каталог задачи;
- выводить идентичность задачи из открытых файлов, Markdown-документов, имён
  файлов или истории чата;
- создавать или выбирать альтернативный корень артефактов;
- читать артефакты другой задачи как fallback, пример, источник требований или
  архитектурный контекст.

Работать разрешено только внутри переданного `Task artifacts`.

Значение `Task` в `README.md` должно совпадать с runtime-полем `Current task`.
При несовпадении режим сообщает об ошибке идентичности и прекращает работу, не
пытаясь угадать или исправить runtime-контекст.

## Точка входа

Каноническая точка входа:

```text
.roo/tasks/<TASK>/README.md
```

`README.md` хранит:

- устойчивую идентичность задачи;
- текущее состояние lifecycle;
- назначенную единицу реализации;
- человекочитаемое следующее действие;
- служебные данные о повторяющейся ошибке.

Runtime-метаданные определяют расположение задачи. `README.md` не заменяет
runtime-идентичность.

Каждый режим сначала читает `README.md`, затем — только артефакты, необходимые
его текущему этапу.

## Поток знаний

Sublimation выполняет широкое исследование затронутой части codebase и подготавливает
знания для реализации.

Code не повторяет полный архитектурный анализ. Назначенный `Txx` является
основным пакетом знаний для конкретной единицы реализации, а исходный код
проекта остаётся источником истины.

Роли артефактов:

- `README.md` — минимальное устойчивое состояние задачи;
- `implementation-plan.md` — декомпозиция, зависимости и точки интеграции;
- `implementation/Txx-*.md` — самодостаточный пакет реализации одной единицы;
- `handoff.md` — фактические результаты, проверки, отклонения контрактов и
  знания для следующих этапов;
- `review.md` — результат code review и найденные замечания;
- `qa.md` — результат функциональной проверки и подтверждающие данные.

Не следует создавать один обязательный большой `context.md` для каждой Code-сессии.

Дополнительные артефакты, например:

- `context.md`;
- `sublimationure.md`;
- `api.md`;
- `data-and-state.md`;
- `tests.md`;

допустимы только тогда, когда содержат полезную информацию, которую нельзя
естественно поместить в конкретный `Txx`.

Sublimation обязан помещать выводы, необходимые конкретному `Txx`, непосредственно
в этот `Txx`. Code не должен автоматически читать все дополнительные артефакты.

## Контракт `implementation-plan.md`

`implementation-plan.md` — артефакт декомпозиции и оркестрации, а не дамп всего
контекста исследования.

Если задача разбита на несколько `Txx`, документ описывает:

- целостные границы каждой единицы реализации;
- граф зависимостей и интеграции;
- значимые связи порядка выполнения;
- независимые части работы;
- точки fork/join и интеграции, если они существуют;
- ключевые контракты между единицами реализации.

Граф зависимостей должен оставаться ацикличным.

`implementation-plan.md` описывает зависимости и архитектуру, но не выбирает
текущий runtime-`Txx`.

Готовность `Txx` и назначение следующей единицы вычисляет harness.

`Parallel with` фиксирует только семантическую независимость. Эта связь не
назначает работу и не отменяет `Depends on`.

## Контракт пакета `Txx`

Обязательные разделы:

- `Goal`;
- `Context`;
- `Relevant files`;
- `Required behavior`;
- `Constraints`;
- `Verification`;
- `Status`.

Необязательные разделы добавляются только при наличии полезного содержания:

- `Scope`;
- `Relevant symbols`;
- `Current state`;
- `Relationships`;
- `Consumes`;
- `Produces`;
- `Integration points`;
- `Expected result`;
- `Context notes`.

Не нужно создавать пустые разделы только ради соответствия шаблону.

Простой `Txx` должен оставаться коротким. В него передаются только знания,
необходимые для уверенной реализации.

### Связи

Поддерживаемые семантические связи:

- `Depends on` — требует результаты перечисленных единиц;
- `Extends` — изменяет или продолжает существующий механизм;
- `Integrates with` — объединяет результаты нескольких единиц;
- `Parallel with` — не имеет семантической блокирующей зависимости от
  перечисленных единиц;
- `Blocks` — результат этой единицы необходим перечисленным единицам.

Эти связи описывают модель зависимостей. Они не являются командами scheduler.

Harness вычисляет готовность и выбирает следующий исполнимый `Txx`. Модель не
должна самостоятельно воспроизводить алгоритм планирования.

### `Consumes` и `Produces`

`Consumes` описывает требуемые результаты или контракты другой единицы
реализации.

`Produces` описывает фактический контракт или результат, доступный зависимым
единицам.

Нельзя копировать в зависимый `Txx` полную историю реализации другой единицы.
Связи между единицами должны выражаться через явные контракты, а не расплывчатые
ссылки.

Не следует создавать искусственные `Txx`. Если части работы постоянно изменяют
один и тот же код, разделяют неразделимое состояние или создают больше затрат
на координацию, чем полезной независимости, их следует оставить в одной
целостной единице.

## Распространение изменений контрактов

Запланированный контракт может измениться в процессе реализации.

После завершения `Txx` Code фиксирует фактический результат и обнаруженные
отклонения от плана.

Если новое знание влияет на будущие зависимые или интеграционные единицы:

1. записать фактический результат и проверки в текущий `Txx` и `handoff.md`;
2. обновить только затронутые будущие `Txx`;
3. изменить только поля, затронутые отклонением, например `Consumes`,
   `Constraints`, `Context notes` или `Produces`;
4. не копировать историю реализации или production-код в зависимые артефакты.

Если обнаруженный контракт делает текущую декомпозицию или граф зависимостей
невалидными, Code фиксирует необходимость повторного анализа и возвращает
`Stage Result: BLOCKED`. Code не переводит задачу в `ANALYSIS` вручную и не
перепроектирует молча будущие единицы.

Зависимая Code-сессия перед изменением production-кода выполняет точечную
проверку актуального исходного кода.

Артефакты передают намерение и подготовленные знания, но не заменяют исходный
код как источник истины.

## Версия протокола

Новые артефакты используют:

```text
Protocol Version: 2
```

Совместимость со старыми форматами обеспечивает harness.

При содержательном изменении legacy-задачи новые и обновлённые канонические
данные записываются в формате protocol version 2. Не следует массово
переписывать не связанные с текущей работой legacy-артефакты только ради
формального соответствия.

## Каноническое состояние `README.md`

`README.md` protocol version 2 содержит один канонический блок:

```text
Protocol Version: 2
Task: <TASK>
Status: <TASK_STATUS>
Current Task: <implementation/Txx-*.md or NONE>
Next Step: <one concrete action>
Failure Key: <stable finding id or NONE>
Failure Attempts: <non-negative integer>
Total Failure Attempts: <non-negative integer>
Blocked From: <TASK_STATUS or NONE>
```

`Task` — устойчивая идентичность. Она не меняется на протяжении lifecycle и
должна точно совпадать с именем каталога задачи и runtime-полем `Current task`.

Каждое финальное сообщение `TASK_STATE_V2` копирует `Task` из `README.md`.

Допустимые статусы задачи:

- `ANALYSIS`;
- `PLAN_READY`;
- `READY_FOR_IMPLEMENTATION`;
- `IMPLEMENTATION`;
- `READY_FOR_REFACTOR`;
- `REFACTOR`;
- `READY_FOR_REVIEW`;
- `REVIEW`;
- `REVIEW_PASSED`;
- `QA_READY`;
- `DONE`;
- `BLOCKED`.

### Владение состоянием

Следующие поля принадлежат программному harness:

- `Status`;
- `Current Task`;
- `Failure Key`;
- `Failure Attempts`;
- `Total Failure Attempts`;
- `Blocked From`.

Владение `README.md` подкреплено инструментально, а не только правилом: вне
`Status: ANALYSIS` file-mutation инструменты модели не могут изменять
`README.md` задачи — гейт отклоняет запись. Единственное исключение — bootstrap
новой задачи (см. ниже).

`PLAN_READY` — harness-owned статус, как `BLOCKED`: ни один режим не запускается в
нём и не завершает его, выход — только harness-owned approve-действие.

Lifecycle controller принимает решение на основе текущего состояния и
семантического результата этапа. Runner применяет решение через канонический
writer. Scheduler назначает `Current Task` после вычисления готовности `Txx`.

Модель не изменяет эти поля для управления lifecycle, не выбирает следующий
режим и не назначает следующий `Txx`.

Единственное исключение — bootstrap новой задачи: если `README.md` ещё не
существует, Sublimation создаёт его с `Status: ANALYSIS`, `Current Task: NONE`,
`Failure Key: NONE`, `Failure Attempts: 0`, `Total Failure Attempts: 0` и
`Blocked From: NONE` согласно Sublimation Rules.

После bootstrap все изменения harness-owned полей выполняются только
программным harness. Если режим не наблюдает ожидаемого перехода, он сообщает
фактически увиденное состояние и прекращает работу, не исправляя статус
самостоятельно.

Вне активного назначения реализации используется:

```text
Current Task: NONE
```

Нельзя хранить несколько конкурирующих канонических блоков. Свободный текст о
прогрессе и handoff-заметки не заменяют каноническое состояние.

### Информационное поле `Next Step`

`Next Step` — человекочитаемый указатель. Он не участвует в маршрутизации.

Scheduler обновляет его при назначении единицы реализации. После перехода между
этапами значение может временно описывать уже выполненную работу. Пока это поле
не используется программными потребителями, модель не должна принимать по нему
решения или пытаться исправить lifecycle.

### Учёт повторяющихся ошибок

`Failure Key`, `Failure Attempts` и `Total Failure Attempts` принадлежат
harness.

Модель может сообщить один стабильный `Failure Key` в результате неуспешного
этапа. Lifecycle controller самостоятельно:

- связывает попытку исправления с ключом;
- увеличивает счётчик попыток по ключу;
- увеличивает эпизодный счётчик `Total Failure Attempts` на каждый fix pass
  независимо от ключа, поэтому переименование того же замечания не сбрасывает
  бюджет;
- сохраняет счётчики на время повторной проверки;
- сбрасывает данные после успешного продвижения (бюджет ограничивает один
  remediation-эпизод, а не историю задачи);
- переводит задачу в `BLOCKED`, если исчерпан лимит попыток по ключу
  (`max-attempts`) или эпизодный лимит (`max-total-attempts`).

Модель не вычисляет, не увеличивает и не сбрасывает `Failure Attempts` и
`Total Failure Attempts`, а также не воспроизводит лимиты попыток в rules или
skills.

## Статус единицы реализации

Каждый `Txx` protocol version 2 содержит один блок:

```text
## Status
Status: <TODO|IN_PROGRESS|DONE|BLOCKED>
```

Допустимые значения:

- `TODO`;
- `IN_PROGRESS`;
- `DONE`;
- `BLOCKED`.

Code работает только с `Txx`, назначенным через runtime- и канонический контекст
задачи.

Code может установить назначенному `Txx` значение `IN_PROGRESS` при начале
реализации и `DONE` только после выполнения требуемого поведения и проверок.

Code не выбирает следующую единицу. После изменения состояния текущего `Txx`
harness повторно вычисляет канонический snapshot и выполняет следующее
назначение.

Исправление, запрошенное Refactor, Reviewer или QA, не входит в implementation
DAG и не назначает себе точку возврата. Harness возвращает завершённое
исправление на запросивший этап по сохранённому marker-статусу `REFACTOR`,
`REVIEW` или `QA_READY`.

## Отчёт о результате этапа

Каждый режим завершает сессию одним отчётом, содержащим наблюдаемое устойчивое
состояние и семантический результат этапа:

```text
TASK_STATE_V2
Task: <TASK>
Status: <TASK_STATUS>
Current Task: <implementation/Txx-*.md or NONE>
Stage Result: <RESULT>
Failure Key: <stable finding id>   # optional
END_TASK_STATE_V2
```

`Task`, `Status` и `Current Task` копируются из канонического блока в том виде,
в котором режим их наблюдает. Они сообщаются, а не выбираются моделью.

Для маршрутизации значима только строка `Stage Result`. Она сообщает
семантический итог, но не содержит решения о следующем статусе или режиме.
Lifecycle controller выводит их из текущего статуса и результата этапа.

Правила протокола:

- в ответе должна быть ровно одна строка `Stage Result: <RESULT>`;
- допускается не более одной строки `Failure Key: <id>`;
- значение результата должно быть допустимо для текущего режима;
- нельзя повторять или цитировать marker-строки вне финального отчёта;
- нельзя добавлять routing-поля: следующий режим, resume-режим, новый статус или
  счётчик попыток;
- идентичность режима берётся из runtime child history, а не из ответа модели.

Допустимые результаты по режимам:

| Режим         | Результаты                                                 |
| ------------- | ---------------------------------------------------------- |
| `sublimation` | `COMPLETED`, `BLOCKED`                                     |
| `code`        | `COMPLETED`, `RESCHEDULE_REQUIRED`, `BLOCKED`              |
| `refactor`    | `COMPLETED`, `FUNCTIONAL_DEFECT`, `BLOCKED`                |
| `reviewer`    | `PASSED`, `REQUIRED`, `PRODUCTION_FIX_REQUIRED`, `BLOCKED` |
| `qa`          | `PENDING`, `PASSED`, `FAILED`, `BLOCKED`                   |

`NOT_APPLICABLE` не входит в таблицу результатов этапа: это защитный отчёт
режима, запущенного на несовместимом lifecycle-статусе, — режим наблюдает
состояние, не выполняет работу и не изменяет артефакты. Harness парсит такой
отчёт, но отказывается маршрутизировать по нему для любого режима и
восстанавливает маршрут из канонического состояния; это не `BLOCKED` и не
результат этапа.

Семантика результатов:

- `COMPLETED` — ответственность текущего этапа выполнена;
- `PASSED` — проверка успешно пройдена;
- `REQUIRED` — Reviewer обнаружил замечание, требующее исправления;
- `PRODUCTION_FIX_REQUIRED` — Reviewer обнаружил дефект production-кода;
- `FUNCTIONAL_DEFECT` — Refactor обнаружил функциональный дефект, который нельзя
  исправлять как безопасный рефакторинг;
- `PENDING` — QA не может быть завершён автоматически и ожидает действия
  пользователя;
- `FAILED` — QA подтвердил несоответствие требуемому поведению;
- `RESCHEDULE_REQUIRED` — назначенная единица реализации больше не исполнима по
  внутренней, устранимой harness причине (обнаружена зависимость от другой
  единицы `implementation/`); harness сам пересчитывает DAG, lifecycle не
  останавливается;
- `BLOCKED` — существует проверяемое препятствие, которое harness не может
  устранить самостоятельно (решение пользователя, отсутствующие credentials,
  недоступный внешний сервис, неоднозначное требование).

Для результатов `REQUIRED`, `PRODUCTION_FIX_REQUIRED`, `FUNCTIONAL_DEFECT` и
`FAILED` следует передавать стабильный `Failure Key`, чтобы повторное появление
одного замечания учитывалось как один цикл исправления. Ключ описывает finding,
но не выбирает маршрут.

### Два вида причин: `RESCHEDULE_REQUIRED` и `BLOCKED`

Этап, который не может продолжить работу, обязан классифицировать причину,
потому что две причины имеют противоположный эффект на lifecycle:

- **Внутренняя, устранимая причина** — назначенная единица реализации больше не
  исполнима, потому что обнаружена зависимость от другой единицы
  `implementation/`. Harness устраняет причину сам: паркует единицу
  (`IN_PROGRESS` → `TODO`), сбрасывает назначение и пересчитывает DAG. Этап
  возвращает `RESCHEDULE_REQUIRED`; lifecycle продолжается, а запаркованная
  единица снова становится готовой после завершения зависимости.
- **Внешняя, неустранимая причина** — нужно решение пользователя, отсутствует
  credential, недоступен внешний сервис или требование неоднозначно. Harness не
  может устранить причину сам, поэтому этап возвращает `BLOCKED`, и lifecycle
  останавливается до вмешательства человека.

`BLOCKED` для внутренней, устранимой причины — это deadlock: `BLOCKED`
терминален, а scheduler назначает единицы только в implementation-статусах,
поэтому зависимость, которая сама является `TODO`-единицей, никогда не сможет
завершиться, пока задача заблокирована. Внутренняя причина всегда оформляется
как `RESCHEDULE_REQUIRED`.

Отчёт `TASK_STATE_V2` не записывается в `README.md`.

Если режим запущен на несовместимом статусе, он не имитирует работу другого
этапа и не изменяет артефакты. Несовпадение mode/status обрабатывается
программным harness как невалидный запуск с возвратом к legacy resume-path; это
не является причиной вручную менять lifecycle.

## Состояние `BLOCKED`

`BLOCKED` используется только для реального, проверяемого препятствия, которое
harness не может устранить самостоятельно и которое не позволяет текущему этапу
получить корректный результат. Внутренняя, устранимая причина (зависимость от
другой единицы `implementation/`) оформляется как `RESCHEDULE_REQUIRED`, а не
`BLOCKED`.

Содержательный контекст блокировки записывается в соответствующий stage-артефакт
и `handoff.md`:

```text
Blocker: <verifiable reason>
Unblock Condition: <what must become true>
```

Harness записывает канонический `Status: BLOCKED` и каноническое поле
`Blocked From: <TASK_STATUS>` — статус, в котором задача находилась в момент
блокировки. Модель не пишет и не очищает `Blocked From`: origin записи
возобновления принадлежит harness.

### Возобновление после `BLOCKED`

`BLOCKED` не маршрутизируется по одному значению статуса. Возобновление — это
отдельное управляемое действие harness, а не решение модели.

Возобновление возможно только при одновременном выполнении условий:

- есть явный сигнал пользователя или подтверждённое внешнее событие, что
  `Unblock Condition` выполнено;
- harness выполнил поддерживаемое программное resume-действие, которое
  восстановило корректный stage context.

Resume-действие harness:

1. проверяет, что `Unblock Condition` действительно выполнено;
2. снимает `Status: BLOCKED`, возвращая задачу в stage context, записанный в
   каноническом `Blocked From`: stage-entry статусы возвращаются в свою стадию
   (`ANALYSIS`, `READY_FOR_REFACTOR`, `READY_FOR_REVIEW`, `REVIEW_PASSED`),
   implementation-статусы и legacy-записи без origin — в
   `READY_FOR_IMPLEMENTATION`;
3. fix pass, прерванный блокировкой, возобновляется как повторная проверка
   запрашивающей стадией с сохранённым failure-бюджетом; implementation-resume
   сбрасывает `Current Task` в `NONE` и очищает failure-tracking поля;
4. очищает `Blocked From`, пересчитывает DAG и назначает следующую готовую
   единицу реализации.

Модель не выполняет resume самостоятельно:

- не снимает blocker;
- не меняет `Status`;
- не читает и не изменяет канонический `Blocked From`;
- не сбрасывает failure tracking.

Режим, который продолжает работу после resume, сначала проверяет выполнение
`Unblock Condition` и только затем продолжает этап.

Несовпадение mode/status само по себе не является блокером.

## Состояние `PLAN_READY`

`PLAN_READY` — гейт подтверждения плана между анализом и реализацией. Sublimation
завершает `ANALYSIS` и, когда гейт включён (setting `requirePlanApproval`, default
`true`), задача останавливается на `PLAN_READY` вместо автоматического перехода к
реализации. При выключенном гейте сохраняется прежний переход к
`READY_FOR_IMPLEMENTATION`.

`PLAN_READY` принадлежит harness, как `BLOCKED`:

- ни один режим не запускается в этом статусе и не завершает его;
- stage outcome не покидает `PLAN_READY`;
- выход — только harness-owned approve-действие
  (`LifecycleController.approvePlan` → `resume_implementation`), которое
  возвращает задачу в `READY_FOR_IMPLEMENTATION` и пересчитывает DAG.

До подтверждения пользователь может править артефакты плана; approve перечитывает
DAG с диска. Если после approve нет готовой единицы (например, DAG сломан правкой),
задача остаётся в `READY_FOR_IMPLEMENTATION` с `Current Task: NONE`; повтор — через
команду "continue lifecycle".

Модель не выполняет approve самостоятельно: не меняет `Status`, не выводит
`PLAN_READY` из stage outcome и не назначает реализацию.

## Семантика этапов

Этот файл определяет только общую схему артефактов, протокол результата и
словарь понятий.

Mode-specific rules определяют критерии выполнения конкретного этапа:

- Sublimation исследует задачу, определяет декомпозицию, зависимости, контракты и
  знания для реализации;
- Code реализует только назначенный `Txx` и фиксирует фактический результат;
- Refactor улучшает структуру, не изменяя требуемое поведение молча;
- Reviewer оценивает реализацию и фиксирует замечания и итог;
- QA проверяет требуемое поведение и фиксирует результат проверки.

Выбор следующего `Txx`, маршрутизация этапов и возврат после исправления не
относятся к ответственности режимов. Режим сообщает результат и завершает
работу.

Нельзя дублировать в mode rules или skills:

- алгоритмы scheduler;
- определение задачи через Git;
- выбор корня артефактов;
- таблицу lifecycle-переходов;
- правила возврата после fix pass;
- подсчёт и лимит повторных попыток.

## Совместимость с legacy-артефактами

Legacy-артефакты могут содержать старые заголовки или значения. Их разбор и
нормализация являются ответственностью harness.

При содержательном изменении legacy-задачи:

- сохранять полезную существующую информацию;
- записывать новые канонические поля в формате protocol version 2;
- не выводить другую идентичность задачи;
- не восстанавливать вручную scheduler-state, которое уже вычисляет harness.

Нельзя повторно открывать задачу, устойчиво отмеченную `DONE`, только потому,
что в ней отсутствует новая структура артефактов.

## Владение инструкциями

`.roo/rules/task-artifacts.md` определяет:

- схему артефактов;
- семантику артефактов;
- контракт передачи знаний;
- общий протокол результата этапа;
- общий словарь.

Mode-specific rules определяют семантическую ответственность и критерии
завершения одного этапа.

Skills определяют способы выполнения содержательной работы.

Программный harness владеет детерминированной механикой:

- runtime-идентичностью задачи;
- выбором корня артефактов;
- разбором и валидацией `Txx`;
- вычислением готовности зависимостей;
- выбором следующего `Txx`;
- каноническим назначением реализации;
- маршрутизацией этапов и переходами `Status`;
- возвратом fix pass на запросивший этап;
- терминальными решениями `DONE`, `BLOCKED` и ожиданием QA;
- учётом повторяющихся ошибок и лимитом попыток;
- согласованием состояния;
- tracing и observability.

Rules и skills не должны повторно реализовывать детерминированное поведение
harness.

## Принципы артефактов

Артефакты — устойчивая локальная память между агентскими сессиями.

Исходный код проекта — источник истины.

Если артефакт противоречит фактическому исходному коду:

1. проверить текущую реализацию;
2. следовать исходному коду;
3. обновить только затронутый артефакт.

В артефактах не хранятся:

- стенограммы чата;
- chain-of-thought или скрытые рассуждения;
- большие копии production-кода;
- нерелевантные эксперименты.

Предпочтительны точные ссылки на файлы проекта, классы, методы, API и явные
контракты.
