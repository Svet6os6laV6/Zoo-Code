# Правила Sublimation

## Условия входа

Используй runtime-поля `Current task` и `Task artifacts` без изменений и в
соответствии с `.roo/rules/task-artifacts.md`.

Запрещено:

- определять идентичность задачи по Git или имени ветки;
- искать другой каталог задачи;
- выбирать или создавать альтернативный корень артефактов;
- вычислять следующую единицу реализации;
- назначать `Current Task` вручную.

## Инициализация новой задачи

Если по переданному пути `Task artifacts` отсутствует `README.md`, сначала
создай сам каталог задачи:

```sh
mkdir -p "<Task artifacts>"
```

Замени `<Task artifacts>` точным runtime-значением, переданным harness. Не
вычисляй путь самостоятельно. Каталог должен существовать до открытия или
записи любого файла внутри него.

После создания каталога первым действием записи инициализируй `README.md`
каноническим состоянием:

```text
Protocol Version: 2
Task: <TASK>
Status: ANALYSIS
Current Task: NONE
Next Step: Проанализировать исходный запрос и текущее состояние workspace
Failure Key: NONE
Failure Attempts: 0
Total Failure Attempts: 0
Blocked From: NONE
```

Замени `<TASK>` точным runtime-значением `Current task`.

Полный этап Sublimation выполняется только в следующих случаях:

- текущее состояние — `Status: ANALYSIS`;
- задача новая и `README.md` ещё не существует.

Если Sublimation запущен для другого lifecycle-состояния:

- не выполняй анализ;
- не изменяй артефакты задачи;
- перечитай фактическое устойчивое состояние;
- верни его через `TASK_STATE_V2` с `Stage Result: NOT_APPLICABLE` согласно
  `.roo/rules/task-artifacts.md`.

Не изменяй lifecycle-статус в этом случае. Harness сохраняет задачу на текущем
маршруте.

## Ответственность за анализ

Используй skill `sublimation-task-analysis`.

Не изменяй production-код.

Sublimation отвечает за широкое, но целевое исследование затронутой области
codebase.

Перед планированием исследуй систему настолько, чтобы понимать:

- релевантные точки входа;
- фактический execution flow;
- архитектурные границы и зоны ответственности;
- зависимости и внешние контракты;
- переходы данных и состояния;
- error paths;
- конфигурацию;
- существующие тесты;
- lifecycle и конкурентное поведение, если они важны для задачи.

Не выполняй не связанное с задачей исследование всего репозитория.

Явно определи:

- `Current behavior` — как система работает сейчас;
- `Expected behavior` — как она должна работать;
- разрыв между текущим и ожидаемым поведением;
- ограничения, влияющие на реализацию.

Если имеющихся требований недостаточно, чтобы однозначно определить
`Expected behavior`, не придумывай отсутствующие требования.

В этом случае:

1. зафиксируй `Blocker` и `Unblock Condition` в отдельном содержательном
   разделе `README.md`, вне канонического state-блока; каноническое поле
   `Blocked From` записывает harness и модель его не пишет;
2. запиши полезный контекст блокировки в `handoff.md`;
3. верни `Stage Result: BLOCKED` и стабильный `Failure Key`;
4. задай пользователю один конкретный вопрос, ответ на который необходим для
   продолжения.

Не записывай `Status: BLOCKED` самостоятельно. Harness выполняет этот переход
по результату этапа.

## Планирование реализации

Создай `implementation-plan.md` как карту декомпозиции и оркестрации, а не как
дамп результатов исследования.

План должен описывать, когда это применимо:

- целостные единицы реализации;
- зависимости и интеграционные связи;
- порядок выполнения или волны;
- независимые части работы;
- точки fork/join;
- точки интеграции;
- контракты, которыми обмениваются единицы реализации.

Граф зависимостей должен оставаться ацикличным.

Создай как минимум один файл `implementation/Txx-*.md`.

Декомпозируй реализацию рекурсивно до минимальных законченных и отдельно
проверяемых единиц работы.

Предпочитай несколько небольших последовательных `Txx` одной крупной `Txx`,
если части могут быть реализованы и проверены по отдельности.

`Txx` не обязана быть независимой feature и не обязана выполняться параллельно.
Последовательные зависимости `T01 → T02 → T03` являются нормальной формой
декомпозиции.

Если одна `Txx` содержит несколько самостоятельных изменений поведения,
архитектурных слоёв, integration points или проверяемых результатов, раздели её.

Останови декомпозицию только тогда, когда дальнейшее разделение создало бы
механические шаги без самостоятельного проверяемого результата.

Sublimation описывает семантику зависимостей. Runtime-готовность и выбор
следующего `Txx` являются ответственностью harness.

## Пакеты знаний `Txx`

Каждый `Txx` должен быть самодостаточным пакетом знаний для одной Code-сессии.

Применяй семантическое сжатие: включай только информацию, необходимую для
уверенной реализации конкретной единицы.

Добавляй релевантные:

- цели;
- текущее поведение;
- требуемое поведение;
- файлы и символы;
- контракты;
- ограничения;
- точки интеграции;
- требования к проверке.

Не копируй в `Txx` широкое исследование, историю чата или большие фрагменты
production-кода.

Для связанных единиц явно указывай семантические отношения из artifact
contract:

- `Depends on`;
- `Extends`;
- `Integrates with`;
- `Parallel with`;
- `Blocks`;
- `Consumes`;
- `Produces`.

Зависимые `Txx` должны получать необходимые результаты и контракты, а не
историю реализации своих зависимостей.

Не требуй чтения другого `Txx` по умолчанию, если необходимый контракт можно
ясно выразить через `Consumes` или локальный контекст текущей единицы.

Создавай дополнительные общие исследовательские артефакты только тогда, когда
они дают реальную ценность.

Любой вывод, необходимый для реализации конкретного `Txx`, всё равно должен
быть представлен внутри этого `Txx`.

## Handoff

Создай или обнови `handoff.md`, включив устойчивую информацию, необходимую
последующим этапам.

Записывай только полезные факты:

- важные архитектурные выводы;
- проверенные предположения;
- ограничения, обнаруженные при анализе;
- контракты, которые должны сохранить последующие этапы;
- неразрешённые блокеры.

Не используй `handoff.md` как стенограмму и не дублируй в нём весь
`implementation-plan.md`.

## Завершение анализа

Перед завершением этапа проверь, что:

- `Current behavior` и `Expected behavior` определены однозначно;
- `implementation-plan.md` отражает выбранную декомпозицию;
- существует как минимум один `Txx`;
- зависимости и контракты `Txx` явно описаны там, где они нужны;
- каждый `Txx` содержит достаточно знаний для своей Code-сессии;
- для каждой единицы определена необходимая проверка;
- `handoff.md` содержит полезные межсессионные знания;
- артефакты соответствуют `.roo/rules/task-artifacts.md`.

После успешного анализа не записывай lifecycle-переход самостоятельно. Верни
`Stage Result: COMPLETED`; переход состояния и назначение единицы выполняет
harness.

Не выбирай первый готовый `Txx` и не переводи ни один `Txx` в `IN_PROGRESS`.

Harness отвечает за:

- вычисление готовности;
- выбор следующей единицы реализации;
- переход из `ANALYSIS`;
- назначение `Current Task`;
- изменения `README.md`, выполняемые scheduler;
- очистку или сохранение failure-tracking полей по правилам lifecycle.

Не запускай этап Code самостоятельно.

Перед завершением сессии повторно прочитай каноническое состояние задачи и
верни `TASK_STATE_V2` согласно `.roo/rules/task-artifacts.md`.

Envelope сообщает результат этапа Sublimation. Он не должен повторно
реализовывать scheduler, выбор задачи или lifecycle routing.
